Cinco conceptos, no más

01

GameObject y Component

Un GameObject es un contenedor vacío. Todo lo que hace algo es un Component que le cuelgas. El objeto Robot lleva cinco.

Componer capacidades en vez de heredar clases.

02

Transform y jerarquía

Un hijo se mueve relativo a su padre. Por eso el brazo sigue al chasis gratis, y el codo hereda la inclinación del hombro.

La jerarquía es la cadena cinemática. No hay que programarla.

00:08 – 00:20

Cuándo corre tu código

03

MonoBehaviour y su ciclo

Awake prepara, Start arranca, Update corre cada frame. Un frame dura Time.deltaTime segundos, y ese número cambia constantemente.

Multiplicar siempre por deltaTime: si no, el robot corre más en un PC potente.

04

Update vs LateUpdate

LateUpdate corre después de todos los Update. La cámara sigue al robot ahí.

Si ambos corrieran en Update, el resultado dependería del orden de los componentes y la imagen temblaría.

00:08 – 00:20

Las capas las vigila el compilador

05

Assembly Definitions

Tres .asmdef parten el código en tres bibliotecas. Core no puede ver a Game; Game sí ve a Core.

Si alguien mete la UI dentro del dominio, deja de compilar.

—

Y uno que no usamos: física

No hay Rigidbody. El robot no se empuja: se le escribe la posición cada frame desde la telemetría.

Un robot real tampoco «rebota». Su posición se lee de los sensores.

La pieza central

El contrato entero

public interface IRobotLink : IDisposable
{
    LinkStatus     Status    { get; }   // desconectado / conectando / conectado
    RobotTelemetry Telemetry { get; }   // la unica fuente de verdad
    ArmLimits      Limits    { get; }   // topes que este enlace hace cumplir

    void Connect();
    void Disconnect();
    void SendDrive(DriveCommand command);
    void SendArmTarget(ArmPose target);
    void Tick(float deltaTime);
}

Todo lo de arriba habla solo con esto, y jamás sabe qué hay debajo.

Un detalle que no es un detalle

Por qué Tick está en el contrato

Parece cosa de la simulación. No lo es.

En la simulación

Integra el modelo físico: avanza el robot, mueve los servos, gasta batería.

En el enlace real

Vaciará la cola de mensajes de red. Solo el hilo principal de Unity puede tocar la escena, y Tick es ese momento.

Ponerlo en el contrato desde el principio evita que la versión real necesite un mecanismo distinto al de la simulada.

private void Update()
{
    Link.Tick(Time.deltaTime);                    // 1. el enlace avanza

    if (Link.Status == LinkStatus.Connected)
        ApplyTelemetry(Link.Telemetry);           // 2. la escena obedece
}

private void ApplyTelemetry(RobotTelemetry t)
{
    _chassis.SetPositionAndRotation(t.Position, t.Rotation);
    _arm.Apply(t.Arm);
}

Seis errores reales
de este proyecto

No son ejemplos inventados. Los seis ocurrieron construyendo esto y se corrigieron.

Ángulos y acumuladores

1 · eulerAngles.y no es un rumbo fiable

El robot conduce hacia un lado distinto del que mira.

Con rotación en X o Z, la descomposición a Euler devuelve una Y que no coincide con la dirección real. Solución: proyectar el forward sobre el suelo y usar Atan2.

2 · Acumular un objetivo sin recortarlo (windup)

La articulación «se bloquea» en el tope y tarda segundos en responder al invertir.

El objetivo interno seguía sumando: 200, 330, 600… Al invertir había que desenrollar todo el exceso. Solución: recortar también el objetivo local. Es lo que satura un PID.

3 · Restar ángulos que dan la vuelta

Giros fantasma de 359° cuando el rumbo pasa de 359 a 0.

Solución: Mathf.DeltaAngle, nunca una resta cruda.

Editor, orden y tiempo

4 · Clicar en la vista Scene selecciona el hijo

Mueves «el robot», se queda donde lo sueltas y luego gira descentrado.

El raíz no tiene geometría: Unity selecciona el hijo con el renderer. Solución: seleccionar desde el panel Hierarchy.

5 · Mover la cámara en Update

La imagen tiembla de forma sutil e intermitente.

Robot y cámara se movían en el mismo momento del frame: dependía del orden de ejecución. Solución: LateUpdate.

6 · Suavizado que depende de los FPS

La cámara se siente distinta en un portátil que en un PC potente.

Lerp(a, b, v * deltaTime) no es independiente del framerate. Solución: 1 - Mathf.Exp(-k * deltaTime).
